# privileged-trigger-runs-pr-code
langs: github-actions

When: Workflow on `pull_request_target`, `workflow_run` or `issue_comment` checks out or fetches the PR head (`ref:` from the PR, `refs/pull/…`, `workflow_run.head_sha`, `gh pr checkout`) or builds it.
Ask: Does any step run content the PR controls: a build or test script, a Makefile, `npm install` (the `preinstall`/`postinstall` scripts of any dependency the PR adds), a tool that loads a config file from the tree, a local `./` action? These triggers run with the repository's secrets and a token that can write, so the PR author gets both. Their default-branch cache is read-only unless the workflow, the job or a reusable workflow it calls declares `cache-mode: write` or `write-only`, which lets the PR save entries that later `push` and `schedule` runs restore. actions/checkout v7, and since July 2026 floating major tags such as `@v4`, refuse a fork PR's head or merge commit under `pull_request_target` and PR-triggered `workflow_run` unless the step sets `allow-unsafe-pr-checkout: true`; a SHA-, minor- or patch-pinned older checkout, `git fetch` or `gh pr checkout` in `run:`, and `issue_comment` are not blocked. Referencing no secrets is no defence: the job's `GITHUB_TOKEN` is still on the runner, and every later step in the job shares its files. A `types: [labeled]` gate with a `safe to test` label races: the author can push a new commit after the label is applied and before the checkout.
Not when: `actions/checkout` with no `ref`, which checks out the default branch · the PR tree is only read as data (a diff, a grep) and no script, hook or install runs on it.
Report as: `<workflow>` on `<trigger>` runs code from the PR via `<step>`: any fork author gets `<secrets / write token / cache>` and can take over the repository; fix: build and test under `pull_request` (no secrets, read-only token) and do the privileged part in a `workflow_run` job that reads that run's artifacts only as data.
