# dependency-confusion-via-registry-config
langs: python, javascript, java, dotnet

When: Package index or registry config added or changed (`--extra-index-url`, `pip.conf`, `.npmrc`, Maven or Gradle `repositories`, NuGet sources), or a dependency on an internally published package added.
Ask: Can an internal package name also be resolved from a public registry? pip with `--extra-index-url` treats every index as equal and installs the highest version from any of them, so a public upload of the internal name with a higher version wins. npm resolves an unscoped name from the one configured registry, so an internal package is safe only under a scope bound to the internal registry (`@org:registry=` in an `.npmrc` committed to the repository, which overrides user config). uv's default `first-index` strategy stops at the first index that has the name. Gradle takes the first declared repository that has the artifact; Maven tries settings repositories, then the project's and parent POMs', then Central, and Central publishes a groupId only to its verified owner.
Not when: one internal proxy registry that mirrors public packages and refuses public uploads of internal names · npm packages under a scope mapped to the internal registry · uv with its default index strategy and the internal index listed first.
Report as: `<package>` can resolve from `<public registry>` through `<config>`: anyone who publishes that name with a higher version runs code in every build and install; fix: `--index-url` to a single proxy (or per-package index pinning), a scope bound to the internal registry, and hash-pinned lockfiles.
