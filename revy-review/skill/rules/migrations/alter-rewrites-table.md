# alter-rewrites-table
langs: any

When: Migration adds a column with a default, identity or stored generated value, or changes a column's type, length or precision on an existing table.
Ask: Is the change metadata-only, or does it rewrite the table and its indexes while holding the lock? Postgres 11+ adds a column with a non-volatile default without a rewrite (`now()` is stable and is evaluated once, so every existing row gets the migration's timestamp). A volatile default (`gen_random_uuid()`, `clock_timestamp()`, `random()`), a serial or identity column, or a stored generated column rewrites the table. A type change rewrites the table unless the old type is binary-coercible to the new one: lengthening `varchar(n)` or converting it to `text` is free, `int` → `bigint` rewrites the table and every index on it. On MySQL, `INSTANT` `ADD COLUMN` needs 8.0.12+, and 8.0.29+ for a position other than last; a `VARCHAR` grows in place only while its length prefix keeps the same size (255 bytes or less vs more, so `utf8mb4` `VARCHAR(63)` → `VARCHAR(64)` copies the table); other type changes, and an FK added while `foreign_key_checks` is on, use `ALGORITHM=COPY`. MySQL silently picks the cheapest algorithm the change supports, `COPY` included; an explicit `ALGORITHM=INSTANT|INPLACE, LOCK=NONE` makes an unsupported change fail instead. Indexes, `NOT VALID` constraints and enum changes: `data/locking-migration-on-large-table`. `SET NOT NULL`: `data/not-null-column-on-live-table`.
Not when: the table is created in the same migration or known to stay small.
Report as: `<statement>` rewrites `<table>` under `<lock>` because `<volatile default / non-coercible type / COPY fallback>`: writes stall for the whole copy during deploy; fix: a constant default with the value filled by a batched backfill, a new column plus dual-write instead of an in-place type change, an explicit `ALGORITHM`/`LOCK`, or an online schema-change tool (gh-ost, pt-online-schema-change) for MySQL.
