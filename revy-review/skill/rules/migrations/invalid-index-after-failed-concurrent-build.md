# invalid-index-after-failed-concurrent-build
langs: any

When: Postgres migration runs `CREATE [UNIQUE] INDEX CONCURRENTLY`, or `REINDEX … CONCURRENTLY`.
Ask: It cannot run in a transaction block, so the migration must opt out: Django `atomic = False`, Alembic `autocommit_block()`, Rails `disable_ddl_transaction!`, a Flyway `executeInTransaction=false` script config, Liquibase `runInTransaction="false"`, an sqlx `-- no-transaction` first line (0.7+), diesel `run_in_transaction = false` in `metadata.toml`. A build that fails partway, through a duplicate key, a deadlock, `lock_timeout` or a cancel, leaves an INVALID index (`pg_index.indisvalid = false`). Queries never use it, but every write still pays to maintain it. On rerun, `IF NOT EXISTS` sees the name and skips, so the migration succeeds without a usable index, and without that `IF NOT EXISTS` the rerun fails on the name. Does the migration drop an invalid leftover before building? Overlaps with the lock rules: `data/locking-migration-on-large-table`.
Report as: `<migration>` builds `<index>` concurrently with `<IF NOT EXISTS / no cleanup>`: after a failed attempt the rerun `<skips the INVALID index and reports success / fails on the name>`, and queries keep scanning `<table>`; fix: `DROP INDEX CONCURRENTLY IF EXISTS` (or a check of `indisvalid`) before `CREATE INDEX CONCURRENTLY`, one index per non-transactional migration.
